# 360 Import Builder

Internal, bilingual consultant tool that consolidates participant respondent files and produces the exact Excel import required by the current production 360 application.

## Audience and purpose

This pack is for BHB/Trend consultants. It accepts multiple files from the participant collector, supports the current legacy collection sheets during transition, and can use an optional questionnaire-allocation export when adding participants to an existing live project. It makes errors and identity conflicts visible before a production workbook can be downloaded.

## Workflow

1. Enter the production project/campaign name when it is not already present in an existing import workbook.
2. Use the single project-workbook picker to add one or more collector files, completed mass-relations templates, supported legacy collection files, allocation exports or existing production imports. The importer detects each format automatically.
3. When an existing production import contains one unique `NumeCampanie` value, the project name is filled automatically; an allocation export without that column still requires the consultant to enter the name.
4. Review participant, role and language totals; correct blocking participant errors; resolve every identity-name conflict. Existing allocation names are preselected where available.
5. Notice every English-language (`EN`) allocation. This is information, not a blocking error.
6. Download the exact A:N production workbook only after all blockers are resolved.

The source ledger keeps every attempted file visible with its byte size, fingerprint state, detected adapter, row dispositions and normalization count. Local checking is shown honestly as pending and blocks production without claiming failure; a settled rejected/unreadable attempt remains blocking until the consultant explicitly removes it or selects a corrected replacement. The optional audit receipt can be downloaded after any source attempt, including a pending or blocked run.

## Automation admission gate

1. **Existing input:** participant collection workbooks plus the optional `Accounts` allocation export already produced by the present 360 operating process.
2. **Steps removed:** manual consolidation, role translation, whitespace cleanup, self-row ordering, project-wide identifier reconciliation and construction of the rigid import workbook.
3. **Finished replacement:** one exact A:N production import workbook; optionally, one separate local audit receipt for diagnosis and traceability.
4. **Errors made impossible or visible:** unsupported/rejected sources, malformed participants, duplicate relationships, role/language errors, identifier conflicts and unresolved name choices block production export and remain source-first/actionable.
5. **Legacy app unchanged:** yes. The tool has no API, database, browser automation, message sending or write-back. Existing files come in; finished local artifacts come out.

## Accepted-input and output matrix

| Input/output | Requirement | Disposition |
|---|---|---|
| Collector workbook | Exact standardized collector headers, optionally including `Criteriu1`–`Criteriu5` | `collector`; parsed and reviewed |
| Mass relations template | `Relatii` sheet with participant/respondent relations, required Manager rows and optional criteria | `mass`; self rows are synthesized and the relations are resolved into the production import |
| Legacy participant workbook | A sheet with `Nume`, `Prenume`, `Email`, `Rol` in any column order; known role aliases only, matched ignoring case, diacritics, spaces, hyphens and underscores; evaluator names read as `Nume Prenume` | `legacy`; RO language assumption is warned |
| Allocation export (optional) | `Accounts` sheet with the six observed headers in the production contract | `allocation`; identifier evidence is reused or conflicts block |
| Existing production import (optional) | A workbook containing the exact A:N production headers, including `NumeCampanie` | `allocation`; identifier evidence is reused, and one unique campaign name can prefill the project field |
| Unsupported/unreadable workbook | Anything else | `rejected`; visible and blocking until remove/replace |
| Production output | All blockers resolved | `import-360-<project>.xlsx`, exact A:N contract |
| Traceability output (explicit secondary action) | At least one source attempt; ready or blocked | `audit-360-<project>.xlsx`, separate from production import |

`src/` is canonical. `deploy/` is regenerated by `npm run build` and must never be hand-edited.

## Privacy

All parsing, reconciliation and workbook generation happen locally in the browser. No uploaded or generated workbook, person, email address, project name or recent-file metadata may leave the device, enter a URL, be logged, or persist in localStorage, IndexedDB or a service-worker cache. **Clear/reset** removes the in-memory session.

GitHub Pages publishes the tool's code and static brand assets; it does not receive the workbooks the consultant opens.

The audit receipt is client-confidential: it can contain project, person, email, source and identifier evidence. It is generated locally only on explicit click and is never persisted by the page. The consultant controls its storage and deletion. Resetting or closing the page clears memory and requires source reload, but cannot delete files already downloaded.

## Diagnosis and recovery

Each blocker names the person/source and the corrective action. Correct the named workbook, use that source card's explicit **Replace** control (or remove and load it again), review and regenerate the outputs. Replacing the optional allocation export clears its prior in-memory state first, so an unreadable replacement can never silently reuse stale identifiers. Removing or replacing one participant source preserves unrelated valid sources, including files that happen to share the same filename.

## GitHub Pages upload

The finished `deploy/` directory is the publishable pack. Upload **the contents of `deploy/`** to the root of a separate public GitHub repository, then enable GitHub Pages from its main branch and root directory. Keep all paths relative and bundle the workbook library locally. Never publish input/output workbooks, browser captures containing real client data or real-data fixtures.

For a local preview, extract the pack and open `deploy/index.html` directly. The build bundles the application into a classic script so controls also work from a `file://` address; keep the full `deploy/` folder together.

## Intentional differences

- **From the current production app:** this tool is a pre-import safety layer. It normalizes and validates data, reuses evaluator identifiers and emits the old application's exact workbook contract, including its self-as-first-Manager quirk. It does not send notifications or modify the live project itself.
- **From the participant collector:** this is an internal project-wide reconciliation surface. It exposes production roles, identifier conflicts, allocation history and export readiness that would confuse or burden participants.
- **From the future platform:** native project enrollment should remove this handoff entirely. The importer remains only as a fallback/migration path (internal note, kept in the private workspace).

## Acceptance boundary

The implementation contract is [docs/production-contract.md](docs/production-contract.md), and the authoritative numbered acceptance list is in the collector's review note (internal note, kept in the private workspace). Workbook structure can be accepted through tests, XML inspection and Excel/LibreOffice reopening. The phrase **production-compatible** is reserved until Vlad completes a controlled import into the old production 360 app and verifies row acceptance, self-sheet assignment, notification creation and identifier reuse; before that, the pack is **structurally validated**.

## Development verification

Run `npm run build` to regenerate the Pages pack and `npm run verify` to rebuild `deploy/`, execute the synthetic reconciliation/workbook/audit/package suite and run the nested-subpath Chromium privacy/reset test. Verification binds copied styles/assets to `src/` and proves the classic direct-file bundle is the deterministic documented transformation of `src/core.js`, `src/app.js` and `src/index.html`. The browser test uses an existing local Playwright installation and never downloads dependencies; set `CODEX_PRIMARY_NODE_MODULES` if Playwright is installed outside normal Node resolution. A managed macOS sandbox may deny Chromium's Mach rendezvous service—in that case the command reports an explicit skip, and the browser test must be rerun outside that sandbox before release.
